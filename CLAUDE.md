# qwakk-game

The Qwakk browser battle royale: a third-person shooter with ducks, hosted as one CapRover app (`qwakk-game`, client and server on one origin) at `play.qwakk.fun` (runbook: `docs/deploy.md`). Current state: Phase 2: a 16-duck battle royale on the Yelova map (plane drop, glide, loot, zone, navmesh bots; Solo, Duo and Squad with parties, knocks and revives), plus always-on 24-duck deathmatch rooms on the Kavren map with navmesh bot fill (launch: one deathmatch room, Kavren, and one battle royale room; `DM_OPEN_ROOMS` and `BR.maxRooms` open more), and Hunt Season, the co-op PvE mode (1 to 4 signed-in ducks draw katanas in Pond Keep, a duck castle on a pond island, and push out through hordes of hunters across four objectives to the Big Hunter's camp, with dash, quack shockwave and Blade Storm skills, bread cannons, a drawbridge and a repairable gate; it gives a duck XP and levels; `docs/hunt-season.md`, the map `docs/pond-keep.md`). npm workspaces: `packages/shared` (pure sim), `apps/server` (Colyseus 0.18 on Node 24), `apps/client` (Vite + Three.js WebGPU). Platforms: desktop browsers (keyboard and mouse, pointer lock) and phone and tablet browsers in landscape (touch controls, `apps/client/src/input/touch/`); both play in the same rooms and parties. The full plan is `../GAME_PLAN.md`; the run, test and benchmark commands are in `README.md`.

Read this file before changing anything here. Agents start without the owner's conversation, so pass these rules on when you brief one.

## Netcode and anti-cheat rules

- The client sends inputs only: sequence (assigned by Colyseus), client tick, move axes, buttons (fire, reload, weapon slot, shoulder side and aim down sights included), yaw, pitch and view time `vt`. Never trust or accept positions, hits or any other result from a client.
- The server owns position, velocity, hits, damage, ammo, reloads, fire rate, inventory, loot, zone damage, kills and timers.
- Sanitize every input on the server (`sanitizeInputFields` via `defineInput({ sanitize })`), cap the turn rate, cap the input buffer and the message size, and rate-limit consumption with the input credit. Which steps run each tick (real inputs, stand-ins for late inputs, late inputs to skip) is decided only in `apps/server/src/inputPacer.ts`; keep it pure and keep its unit tests and `npm run test:net` passing. Fire-rate gates and ammo live in the shared weapon state machine (server copy decides). Per-IP connection and join limits are in place (see Identity and leaderboard rules); keep them on.
- 30 Hz simulation, one patch per tick. Interest management (`interest.ts`): near players every tick, far players at 10 Hz through per-viewer StateView entries. Rewind cap 230 ms (`COMBAT.maxRewindMs`).
- Anti-wallhack (battle royale and the deathmatch on map_v1 maps, `interest.ts` + `visibility.ts`, numbers in `VIS`): a client gets no pose at all for an enemy it cannot plausibly see. Visible means within `VIS.alwaysRadius`, or within `VIS.maxRange` with a clear line of sight through opaque geometry from the eye or either camera shoulder to several points on the target (with a margin), now or at the lookahead positions; then kept for `VIS.graceMs`. Ducks in the plane are never sent. Shot effects go only to viewers who see the shooter; everyone else in earshot gets `Msg.ShotHint` (weapon, direction, loudness, no position). Kill messages carry the victim's position only to viewers who saw it. Damage indicators carry a direction, never the attacker's position. Movement mode and action are on the culled pose entries, not the public player state. Loot items are per viewer and line-of-sight gated too (`br/itemViews.ts`: added when seen, stale copies until the spot is seen again). The deathmatch culls the same way on map_v1 maps (`IslandRoom.cullHidden`); only the greybox deathmatch keeps everyone in view. One deliberate mode exception: the deathmatch caped hero is a public objective like the pickups, so every `DM_HERO.pingEverySeconds` (5 s) everyone but the hero gets `Msg.DmHeroPing` with the hero's position rounded to a `DM_HERO.pingGrid` (10 m) grid (`apps/server/src/dmHero.ts`, shown on the HUD compass). Never a pose, never finer or more often, and nothing else about the hero (its pose, flight and energy stay culled or owner only). The culling re-tests a third of the viewers each tick (`updateInterest` with `part`) so the ray casts do not spike; its cost grows with humans times ducks.
- Battle royale state the server owns: plane ejection (the Deploy button is a request; the server places the duck at the plane), pickups and crates (the Use button is a request; `br/loot.ts` checks reach and line of sight, opens a closed crate, takes what fits by the capacity rules in `inventory.ts`), inventory requests from the inventory screen (`Msg.Inv` drop and take: validated in `BrRoom`, same reach, sight and inventory rules, rate limited per duck), inventory, carrying capacity, armor, backpack and durability (`items.ts` and `inventory.ts` math, `.view()` fields), the zone and its damage, placements. A crate's open state reaches a viewer through the per-viewer item views like any loot; a closed crate's contents are never sent. Heals and the drop (freefall, glider, landing) are part of the shared sim (`heal.ts`, `drop.ts`) so the client predicts their movement; the server's copy decides.
- Deathmatch kill stacks and the caped hero (`docs/deathmatch-rewards.md`): the server grants and clears them (`dmStacks.ts`, `dmHero.ts`) and writes them into the sim's packed `dmBuff` field (`dmBuffs.ts`); the stack speed bonus and the hero's flight (`heroFlight.ts`, numbers in `KILL_STACKS` and `HERO_FLIGHT`) are part of the shared sim so the client predicts them. Stack damage, hero health, points and the pick interval are server only (admin settings `dm.killStacks`, `dm.stackDamagePercent`, `dm.hero*`). PlayerState is near Colyseus' 63 field limit: pack new per-duck state where possible.
- TPS hit rule (`packages/shared/src/shot.ts`): a ray from the camera through the crosshair finds the aim point, then the server traces from the muzzle to that point; a wall in front of the muzzle stops the shot. Hitboxes (`hitbox.ts`) are a head sphere plus a body capsule per stance, never skinned meshes, and they follow the visual duck, not the movement capsule. Keep them in sync with the art when the duck changes. One hitbox table serves every character: characters (`packages/shared/src/characters.ts`) are looks only, share the classic skeleton exactly and keep accessories inside the classic silhouette (checked by `validate_glb.py` and `apps/client/test/characterModels.test.ts`). Never give a character its own hitbox, speed or weapon numbers.
- Weapons are part of the shared sim (`combat.ts`, numbers in `weapons.ts`): fire rate, ammo, reloads and switching are decided by the server's copy. Aim down sights is a held input button stepped in the sim (`ads.ts`, numbers in `ADS`): its ramp sets spread, recoil and move speed on both sides, so the server's shot matches the client's. The camera moves in along the shoulder line, never off it, so the aim ray in `shot.ts` still matches the crosshair. The client predicts shots for feedback only; damage and kills come from the server, never predicted.
- Lag compensation uses our own history (`apps/server/src/lagComp.ts`). The shooter's `vt` is client-chosen, so it is bounded by the round trip the SERVER measures (`rttProbe.ts`, WebSocket ping frames) plus interpolation delay and a margin, and by the 230 ms cap (`Deathmatch.maxRewindFor`). Bots never rewind.
- Spread trade-off: the spray PATTERN is deterministic and predicted; the RANDOM part of the spread is seeded with a per-round server secret (`spreadSeed`), so it cannot be predicted or cancelled by a cheat. The client predicts its tracer and hit marker with a local guess; the server's shot is authoritative and is what other players see. Do not send the secret to clients.
- Bots (`bots.ts`, deathmatch `dmBot.ts` and battle royale `br/brBot.ts` on the recast navmesh in `nav/`) act only through input frames on the same path as players and see only what is in line of sight (`SIGHT_QUERY_GROUPS`: bushes and hedges hide). They read only public match facts (plane route, announced zone) and loot they can see. No wallhack, no aimbot.
- Stand-in steps (a stalled player) never fire.
- Touch controls (`apps/client/src/input/touch/`) are an input device only: they feed the same `Controls` state as the keys and mouse (stick axes, held and latched buttons, look drags) and send nothing of their own. No new messages, no positions or results; `packages/shared` does not know about touch. Desktop keeps keyboard and mouse with pointer lock exactly as before; a touch laptop shows the touch layer only after a touch on the pause card. Every touch number lives in `input/touch/constants.ts`; the pure stick, look and finger code is unit tested (`apps/client/test/touchInput.test.ts`) and `e2e/mobile-touch.ts` drives it with real touch events.
- Owner-only state uses `.view()` schema fields plus a per-client `StateView`.
- Duck Plaza, the hub between matches (`docs/duck-plaza.md`; shared `hub/`, server `hub/HubRoom.ts`, client `src/hub/`): no combat at all. Inputs are the match input frame sanitized by `sanitizeHubInput` (movement buttons only) on both sides; the server steps the shared `stepPlayer` and owns every position; the owner reconciles only `HUB_SIM_FIELDS` (keep every other sim field unchanged by those buttons, or prediction breaks). Its own small schema (`hub/schema.ts`), never PlayerState. Portals are decided on the server's position (`portalAt`); the client then joins the mode like any Play. Invites, answers, emotes and chat are rate-limited requests the server checks; an accepted invite puts both ducks in a party (the hub opens it server side, codes go only to those two ducks, the inviter first). Interest is bandwidth only (near, far, nothing by distance; no culling is needed where nobody fights). Never send a player id, token or address from it; the team marker is a per-room number, not the party code.
- Hunt Season (`docs/hunt-season.md`; shared `raid/`, server `raid/` and `RaidRoom.ts`, client `game/raidClient.ts`):
  - Hunters (and dogs) are server-only AI actors, not seats and not bots: no input frames, no client prediction, a kinematic navmesh mover (`raid/hunterMover.ts`) that never pushes a duck (so a duck's prediction stays exact). They follow the bot fairness rules all the same: line of sight only (`SIGHT_QUERY_GROUPS`), a reaction delay and an aim error that settles, a random spread the client cannot predict, a visible telegraph before every attack (the rifleman's laser and glint, the boss's wind-up, the dog's lunge, the decoy's honk), no shot without a clear line when it fires, bullets stop at walls (`BULLET_QUERY_GROUPS`). No aimbot, no wallhack.
  - Visibility rule: hunters, traps and drops are public room state, sent to everyone in the run every tick regardless of line of sight. Deliberate: they are AI enemies of a co-op mode, not human opponents, and every duck in a run is an ally (team 1, always in each other's view as in the team modes), so seeing them gives no human an edge over another. Never put anything about a duck into the hunter state, and never use this exception in a mode where humans fight humans.
  - Hits on hunters follow the TPS hit rule with lag compensation (`raid/hunterHistory.ts`, the same window and cap as the ducks'); hunters never rewind (their shots use the ducks' current positions). Hunters have their own hitbox table (`raid/hunters.ts`, from the art contract), next to the one duck table; `HitTarget.shape` marks a non-duck target, and ducks never carry one.
  - Every number of a run the server alone decides is a `raid.*` admin setting (gate health, gate damage and repair, drawbridge timings, raft speed, cannon damage, splash, knockback, reload and heat, katana and skill damage, crit, stagger, knockback, storm meter and combo (`raid.blade.*`), objective counts, crate health and pack pacing (`raid.push.*`), the live cap, hunter health and damage, reaction, aim error, spread, upgrades, drops, rooms). What the client simulates or draws stays a constant (the cannon's flight and arc limits `CANNON`, the reach of the keep's controls `KEEP`, the katana's timings and cooldowns `BLADE`, `DASH`, `QUACK`, `STORM`). Upgrades never change what the client simulates. Do not add PlayerState fields: raid-only duck state goes to its owner as messages (`Msg.RaidSelf`, `Msg.RaidOffer`); a card pick (`Msg.RaidPick`) is checked against the offer.
  - The keep and the duck sim (Pond Keep, `raid/keep.ts`, `raid/man.ts`; why in `docs/hunt-season.md`, Moving parts): no collider a duck walks against may change during a run. The keep reaches the sim only as packed bits the server writes and both sides then simulate alike: the trap root (`ex` bits 19 to 24), the manned cannon (`ex` 25 to 27, set and cleared by the sim itself on Use and Jump presses at the static stand spot) and the cannons others man (`ex` 28 to 31, server), the closed drawbridge (`dmBuff` bit 4 `KEEP_CLOSED`: the sim refuses a step onto the static deck) and the broken gate (`dmBuff` bit 5 `KEEP_GATE_OPEN`: the duck's movement queries leave out the static duck-only gate leaves, `CG.DuckOnly`). The drawbridge deck and the gate leaves are static colliders built from the map data on both sides. What blocks hunters (the gate's line, a raised bridge's gateway, deep water) is their server-only mover and route rules (`raid/travel.ts`), never a duck collider and never a navmesh change. Bullet and sight blockers for the gate and the raised bridge are colliders with Bullet and Sight bits only, switched by their groups on the server (`setToggle`); keep Move and Opaque off them. Cannon loaves are server projectiles; the client predicts only the feel of its own shot. Do not add another keep part that moves ducks without a sim bit and a replay test (`packages/shared/test/keep.test.ts`).
  - The katana (Hunt Season only; `raid/blade.ts`, `raid/arc.ts`, server `raid/blade.ts`): the skill buttons (`Button.Dash`, `Quack`, `Storm`, bits 16 to 18, `SKILL_BUTTONS`) are masked off by every other room's sanitize (`GameRoom.allowSkills`), stand-in steps never press them and hold Fire as it was while the katana is out. The swing, combo, buffered press, charge, cooldowns, storm and dash are shared sim state packed into a katana duck's spare fields (a katana duck has no rifle, grenades, rockets or hero): `mag0` (bits 0 to 3 the act, 4 the buffered press, 5 to 7 the charge), `res0` (ticks into the act), `ex` bits 0 to 6 (dash) and 7 to 14 (quack), `dmEnergy` (the storm meter, written by the server, or 128 plus the storm's ticks left); `ex` 15 to 18 are free and 19 to 31 stay the keep's. Keep it that way: no PlayerState field, and a replay test (`packages/shared/test/blade.test.ts`) for any change. Hits are server only: the sim reports the landing swing (`lastBlade`), the server sweeps its shape against the lag compensated hunter history at the step's view time (same window and cap as a shot), walls stop a cut (`BULLET_QUERY_GROUPS`). The client predicts the feel only (trail, hit-stop, arcs); damage, combo, kills and the meter come from the server (`Msg.RaidHits`, the state). The deathmatch and the battle royale never hand out the katana.
  - XP and levels: granted only by the game server at the end of a run (`RaidRoom.recordResult` to `recordRaid`, `meta/raid.ts`), once per run id, recomputed there from the run numbers with the shared formula (`raid/progress.ts`). Never from a client message; no HTTP route writes XP, levels or raid results, and none may be added. Levels are cosmetic progress only: they never give power in any mode (the deathmatch and the battle royale stay as fair as before).

## Identity and leaderboard rules

- Identities: guests (a nickname plus a server-assigned `#tag`, a server-signed device token that carries the player id, traded for a 24-hour session token) and accounts (`docs/accounts.md`: email sign-in with a 6-digit code, up to 4 ducks per account, each a `players` row with `account_id` and `slot`; picking a duck trades the account session for the same 24-hour session token with `account` and the duck's `look`). Never accept a player id, name, tag, look or account flag from a client message; rooms take them from `verifySession(token)` (`apps/server/src/meta/index.ts`).
- Guests play Deathmatch only: the matchmaking guard (`checkAccount`, `accountOnly.rooms`: battle royale and Hunt Season) and `BrRoom.checkAdmission` and `RaidRoom.checkAdmission` refuse a guest, and a party with a guest, a battle royale or a Hunt Season room (`ACCOUNT_ERROR` in `packages/shared/src/accounts.ts`). Keep every check.
- Account rules: codes are CSPRNG, stored only as an HMAC, 10 minutes, 5 tries, one per address, limited per address and per IP (Turnstile on "send code" when configured); answers never reveal whether an address has an account; account sessions are revocable rows (no IP or user agent stored); emails, codes and tokens are never logged in production. Sign-up needs the terms and 16+ box (stored with `LEGAL_VERSION`); the news opt-in is unchecked by default and every choice is logged with `MARKETING_TEXT_VERSION`. Deleting a duck or an account deletes its rows and anonymises its match rows. `SMTP_PASS` lives only in the server environment. The dev mail sink and `GET /api/test/mail` exist only outside production with test hooks.
- The leaderboard is written only by the game server through `recordMatch`. No HTTP route writes match data, and none may be added. Bots are stored but never ranked. In-game stats only: no prizes, no tokens, no wallet links.
- Characters: the `character` join option is a catalog id (`isCharacterId`); the matchmaking guard drops anything else and the room seats unknown or missing picks as the classic duck (`characterFromOption`). It is public (`PlayerState.character`); bots get the least worn duck (`pickBotCharacter`).
- Names: 3 to 16 of `A-Z a-z 0-9 _`, checked by `names.ts` against `blocked-names.json` (English and Turkish slurs and insults, staff and brand impersonation). Extend the list there, not in code, and add a test case.
- Limits per IP (in memory only, never stored): joins (`allowJoin`), new game rooms (`allowCreateRoom`, through the matchmaking guard in `apps/server/src/matchmaking.ts`, which also caps open battle royale rooms, filters join options and keeps the deathmatch rooms join only), lobby connections (`allowLobby`), open WebSockets (`CONNECTIONS_PER_IP`, 16, IPv6 per /64, checked at the upgrade), session creation, leaderboard reads. Read `X-Forwarded-For` only through `TRUST_PROXY`.
- Parties (`apps/server/src/party/`): one private Colyseus room per party, the party code as its room id, joined by code only (`joinById`); the matchmaking guard refuses `join` and Quick Play into a party and rate-limits party creation and joins by code per IP (`allowPartyCreate`, `allowPartyJoin`). The party sends names, tags, the leader and who is in a match, never player ids or tokens. Game rooms look a player's party up in the registry (`party/registry.ts`) by the player id from `verifySession`, never from a client message; the leader's "go" is only forwarded for a room the leader holds a seat in.
- Teams: battle royale rooms are Solo, Duo or Squad (`team` join option at creation only, `TEAM_SIZES`); `br/teams.ts` places a party on one team and holds seats for its followers. A deathmatch gives a party an ally group (`Seat.team`). Same nonzero team: no damage (the hit path skips allies, shots pass through them), always sent to each other by the interest management regardless of line of sight (the `ally` option of `Interest`; enemies stay culled exactly as before), and the per-team `mates` entries (health, knocked, revive) go only into teammates' views. Knocked (`PlayerSim.down`, set by the server) is part of the sim for the crawl only; knock, bleed out, revive (hold Use, `KNOCK`), team elimination and team places are server rules in `battleRoyale.ts`. Results stay written only by `recordMatch` (team modes pass `field` = teams).
- Name tags (client, `game/nameTags.ts`): faint, small labels within 12 m of the player, fading after 6 m. No self label or boxes. In Duck Plaza (no combat) the labels (`hub/labels.ts`: name#tag, the level badge, speech bubbles) reach `HUB.labelRange` and still never show through a wall. The range applies to allies too; allied wall markers remain only nearby. Enemies still need a received pose and a current clear camera line to the real head or chest. Never draw anything about an enemy the client did not receive.
- `QWAKK_TEST_HOOKS=1` (tests only, refused when `NODE_ENV=production`) lets a client hurt its own battle royale duck for the revive e2e, skip or take Hunt Season objectives, spawn hunters, packs and hordes and fill the storm meter for tests and screenshots (`dev:raid`), and exposes the dev mail sink's codes to the e2e. Never enable it on a deployed server.
- Lobby rooms: the menu's live room list is Colyseus' built-in LobbyRoom (`apps/server/src/lobby.ts`, battle royale and deathmatch rooms only). A room's listing metadata (`RoomListing` in `packages/shared/src/lobby.ts`) is public: never put names, player ids, IPs or tokens in it. The start rule lives in `BattleRoyale` (`minHumans`, `countdownSeconds` in `BR`).
- Deathmatch rooms are static: `DM_ROOMS` (`packages/shared/src/lobby.ts`) are created by the server at start (`index.ts`, room id = the entry's id, `autoDispose` off) and never by a client: the guard refuses `create` and turns Quick Play's `joinOrCreate` into `join` (the open room with the most humans). Humans plus bots are always `MATCH.players` while anyone plays or watches (`Deathmatch.fillBots`); an empty room holds no seats and its tick loop sleeps (`idleWhenEmpty`). One server instance only: replicas would each open the same rooms.
- The deathmatch map is `MATCH.mapId` (`QWAKK_DM_MAP` overrides it for one run). Spawns come from the map's `dmSpawns` (`[x, y, z, yaw]`) or are derived (`dmSpawns.ts`); bots keep their goals inside `playArea.ring`.
- `SESSION_SECRET`, `TURNSTILE_SECRET`, `SMTP_PASS`, `ADMIN_PASSWORD_HASH` and `ADMIN_TOTP_SECRET` live only in the server environment; never commit them. Tests mock Turnstile and never call Cloudflare.
- Schema changes are new files in `apps/server/db/migrations/`; never edit an applied one. Update `docs/privacy-notes.md` when stored data changes.
- The menu (`apps/client/src/ui/menu/`) must not import game modules statically: the game bundle is a dynamic import so the menu paints first (the 3D ducks of the character select come from `src/menuHero/`, also a dynamic import). After the character select (or a guest's name and look, `guestCard.ts`) the menu enters Duck Plaza (`src/hub/`, in the game bundle); the old main menu's functions live in the plaza's sheet (`hubSheet.ts`, Esc), including a plain list of the modes for devices where the plaza cannot draw. Menu copy lives in `copy.en.ts` and `copy.tr.ts` (no em dashes). The legal pages (`/terms`, `/privacy`, `/cookies`) are built from `docs/legal/` at build time.

## Admin panel rules

The admin panel (`play.qwakk.fun/admin`, server `apps/server/src/admin/`, UI `apps/admin/`) lets the owner run the live game: dashboard, runtime settings, moderation, notices and maintenance, audit log. README (Admin panel) and `docs/deploy.md` (2c) have the details.

- Off unless both `ADMIN_PASSWORD_HASH` and `ADMIN_TOTP_SECRET` are set and valid (`npm run admin:setup` makes them and writes nothing to disk): then every `/admin` path is the plain 404 of an unknown path. Secrets only in the server environment, never in the repo, an image, a log or the audit log.
- Local `npm run dev` opens no browser. It starts the local database, client and watched admin build, using the root's ignored `.env` plus existing server environment for manual admin login (exported values win). Local `.env` secrets go only to the server child, never Vite or a build; the file stays out of Git and Docker. Only explicit `npm run dev -- --open` generates temporary credentials and opens an authenticated Chrome preview. `Ctrl+C` must stop its full child process groups and any preview browser. Never leave a separate preview stack running alongside it.
- Login is password (scrypt, async) plus TOTP (6 digits, 30 s, one step of drift, a used step never again), with per-IP and global lockout and rate limits in memory, constant-time compares. The session is a `__Host-` HttpOnly Secure SameSite=Strict cookie signed with a per-process key and held in server memory (12 h, 2 h idle, logout ends it). Every POST must carry this server's own Origin (never another origin, not even `ALLOWED_ORIGINS`: a page on qwakk.fun is same-site), API writes are JSON only. Never log passwords, codes or cookies.
- The admin bundle is never public: it builds into `apps/admin/dist` (served from `QWAKK_ADMIN_DIR`, `/srv/admin` in the image), outside the client dist, and the server serves its files only to a valid session. The login page is self-contained HTML with no script. `apps/client` must not import from `apps/admin` or name admin routes; after changes check that `apps/client/dist` has no admin code (the image build fails if it finds `/admin/api`).
- No client-trusted admin data: the server validates every field (settings are typed and clamped in `settings/runtime.ts`, ids are looked up in the live room table or must be UUIDs), and players never send anything the panel acts on.
- Every mutation writes the audit log (`admin_audit`: actor, time, action, target, old and new value) through `admin/store.ts`. IP addresses are never stored: IP blocks live in memory only (`ops/ipBlocks.ts`) and the audit log names the block and the player, not the address.
- Runtime settings only cover numbers the server alone decides. The constants stay the defaults; game code reads the effective values through `settings/` (`rules.ts` getters at room, round or spawn start, the live bot skill objects, `serverWeapon` for damage), never per tick through a lookup. Anything the client also simulates (movement, fire rate, spread, recoil, ADS, ammo) stays a constant and changes only with a deploy; the panel shows those read only.
- New moderation state is a new migration and a row in `docs/privacy-notes.md`.

## Engineering rules

- `packages/shared` stays pure: no DOM, no network, no timers, no `Date.now()` or `Math.random()` in the sim. `step` functions take state, input and dt and mutate plain number fields. It must stay portable to a Rust/WASM kernel later.
- Determinism is a hard requirement. Client prediction only matches the server when both run the same sim on the same inputs from the same state:
  - Use `dsin`/`dcos` from `math.ts`, never `Math.sin`/`Math.cos`, in anything the sim or map generation computes.
  - The sim rounds its state to float32 every step (that is what the wire carries). Round replayed inputs to float32 on the client before stepping (`session.ts` does this).
  - Map generation uses only the seeded RNG and integer or exact float math. A test checks that `terrainHeightAt` matches the Rapier heightfield (greybox, Yelova and Kavren). A ray straight down exactly on a 4 m grid line can miss the heightfield; probe off the grid lines.
  - Loaded maps (`mapV1.ts`) are pure data: the client and the server build the same collider list in the same order; the e2e compares `mapDefHash` and a sim scenario on the map between Node and Chrome, and the join refuses a client whose map files hash differently (`state.mapHash`).
  - Run `npm test` after any sim change; the determinism tests must pass. The e2e test prints prediction corrections: they should be 0 without packet loss.
- Map data: the map workstream exports to `art/map/export/` and `apps/client/public/models/props/colliders.json`; `npm run map:sync` copies `map_v1.json`, the two `.bin` files and `colliders.json` into `packages/shared/src/maps/<id>/` (`sainte-canard/` for the battle royale, `canard-quarter/` for the deathmatch, `pond-keep/` for Hunt Season, `duck-plaza/` for the hub, whose own props' colliders, `art/map/export/duck-plaza/plaza_colliders.json`, are merged in), the one copy both the server (fs, `maps.ts loadMapV1(id)`) and the client (an `import.meta.glob` over every map folder, `world/sainte/assets.ts`) load. `npm test` fails when a copy is stale. Do not edit the copies by hand. A new map id also needs its navmesh baked into the server image (`deploy/server/build-navmesh.ts` bakes Yelova, the deathmatch map and Pond Keep; the hub has no bots and needs none).
- Collision groups (`collision.ts`): every static collider says what it blocks (move, bullets, sight, opaque) from the map's `kinds` table. Movement queries use `PLAYER_QUERY_GROUPS`, shots `BULLET_QUERY_GROUPS`, bot sight `SIGHT_QUERY_GROUPS`, the camera and the anti-wallhack check `OPAQUE_QUERY_GROUPS`. Use the right one for any new ray.
- Every tunable feel or netcode number lives in `packages/shared/src/constants.ts` (camera numbers in `apps/client/src/camera/tpsCamera.ts`).
- TypeScript is strict with `erasableSyntaxOnly` (no enums, no parameter properties, no namespaces), because the server runs `.ts` files directly on Node 24. Relative imports use the `.ts` extension. Schemas use the `schema()` API, not decorators.
- Use the Colyseus 0.18 built-ins (`defineInput`, `room.input()`, `Predict`, `Reconciler`, `allowRewindState`, `StateView`) unless measured behavior says otherwise, and write down why in the code when you replace one. Read the installed type definitions in `node_modules/@colyseus/*` instead of relying on memory; the 0.18 API differs from older versions.
- Known Colyseus traps found so far:
  - `setFixedTimestep` uses `setInterval(1000 / 30)`, which Node truncates to 33 ms, so some wake-ups run 0 or 2 ticks and remote players hitch. The room uses `tickLoop.ts` instead and sends one patch after each tick; the framework's own patch-timer calls to `broadcastPatch()` are ignored.
  - Keep `patchRate` at the real cadence (1000 / 30). It is advertised to clients, which size their input replay ring from it (a huge value runs the client out of memory). `patchRate = null` without a simulation interval starts a hidden 60 Hz clock ticker.
  - The client state object exists with default values before the first patch is decoded. Wait for `onStateChange` before reading it (the seed!).
  - Reconciler telemetry (`lastCorrection`, `drift`) is only computed when `warnOnDivergence` is set.
  - Taking an input from the buffer acks it. Never take an input you will not simulate, unless a stand-in step already took its place (see `inputPacer.ts`). Buffer overflow also acks dropped inputs.
  - Reliable inputs are one WebSocket message each, so `maxMessagesPerSecond` must leave room for the backlog after a stall, or recovering clients get kicked (code 4002).
  - `Predict` lerp treats any sample gap over 1.5 patch intervals as an idle entity and inserts a held sample. Anything updated slower than every tick (far poses at 10 Hz) must use our own buffer (`farInterp.ts`), or it moves stop-go.
  - Quantized schema fields (`t.quantized`, `t.angle`) snap on assignment and only send real changes, so writing them every tick is cheap.
  - Removing an entry from a client's StateView deletes it on that client.
- The fake network (`apps/client/src/net/netsim.ts`) must deliver strictly in order. One `setTimeout` per message is not enough: browsers round delays to whole milliseconds and can swap messages, which corrupts Colyseus' delta-encoded inputs and patches.
- No WASM threads or SharedArrayBuffer (no COOP/COEP headers needed).
- Keep modules small and readable. No giant single files.
- Dev tools (autopilot, test hook, fake network, `?server=`, spectate) exist only in dev and test builds (`import.meta.env.DEV || VITE_DEVTOOLS === '1'`, `npm run build:test`). Spell that condition out at a dynamic import site so the bundler drops the module from public builds, and check `apps/client/dist` for it after changes. Never gate cheats or tools on a URL flag alone.
